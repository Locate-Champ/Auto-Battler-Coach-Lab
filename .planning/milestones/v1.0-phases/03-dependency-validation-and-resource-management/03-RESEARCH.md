# Phase 3: Dependency Validation and Resource Management - Research

**Researched:** 2026-02-27
**Domain:** Python dependency validation, resource management patterns, import-time checks
**Confidence:** HIGH

## Summary

Phase 3 converts three silent failure paths (missing pyarrow, missing combat_data.json, mismatched Rust extension) into explicit, actionable errors at import/startup time, and adds context manager support to DataLoader for automatic worker pool cleanup. This is a pure Python patterns phase -- no new libraries, no external dependencies, no architectural changes. All changes are to existing files using stdlib mechanisms (`ImportError`, `FileNotFoundError`, `__enter__`/`__exit__`, `ResourceWarning`, `platform` module).

The codebase has clear touch points: `models/data_loader.py` (pyarrow check + context manager), `simulator/core/combat_engine.py` (combat_data.json check), and `simulator/core/engine_wrapper.py` (Rust pre-flight check). The existing `cloud_runner.py` already has a sophisticated Rust extension rebuild hint function (`_rust_extension_rebuild_hint()`) that can be reused or adapted for the engine_wrapper pre-flight. Phase 1 and Phase 2 have already narrowed the pyarrow import to `except (ImportError, OSError)` and established the `_log = logging.getLogger(__name__)` pattern in all models files.

**Primary recommendation:** Implement each requirement as a self-contained change to a single file, following Python stdlib patterns (no new deps). The pyarrow and combat_data.json checks are hard crashes (ImportError/FileNotFoundError). The Rust extension check is a warning with fallback. DataLoader context manager wraps the existing `.close()` method.

### Pattern 1: Import-Time Hard Dependency Check
**What:** Raise ImportError at module level when a required dependency is missing, with an actionable message.
**When to use:** When the module is meaningless without the dependency (DataLoader without pyarrow).
**Example:**
```python
# models/data_loader.py -- top of file, replacing silent fallback
try:
    import pyarrow.parquet as pq
except (ImportError, OSError) as _pyarrow_err:
    raise ImportError(
        "pyarrow is required for DataLoader but could not be imported. "
        "Install: pip install 'pyarrow>=14.0'. "
        "Without pyarrow, the data pipeline silently returns empty iterators."
    ) from _pyarrow_err
```

### Pattern 2: Import-Time File Existence Check
**What:** Verify a critical data file exists at module import time, raising FileNotFoundError with actionable message.
**When to use:** When a data file is essential and its absence causes confusing downstream failures.
**Example:**
```python
# simulator/core/combat_engine.py -- at module level after path construction
_COMBAT_DATA_PATH = Path(__file__).parent.parent / "data" / "combat_data.json"

if not _COMBAT_DATA_PATH.is_file():
    raise FileNotFoundError(
        f"combat_data.json not found at {_COMBAT_DATA_PATH}. "
        f"This file is required for the combat simulator. "
        f"Ensure you have a complete repository checkout: git checkout -- simulator/data/combat_data.json"
    )
```

### Pattern 3: Import-Time Fallback with Architecture Pre-flight
**What:** Try importing a compiled extension, validate architecture match, warn and fall back on failure.
**When to use:** Optional compiled extensions where arch mismatch causes cryptic OSError at first use.
**Example:**
```python
# simulator/core/engine_wrapper.py
import logging
import platform
import struct

_log = logging.getLogger(__name__)

_RUST_ENGINE_AVAILABLE = False
_RUST_ARCH_MISMATCH = False

try:
    from tft_combat_engine import RustCombatEngine
    # Architecture pre-flight: verify pointer size and machine arch match
    _expected_pointer_size = struct.calcsize('P') * 8  # 32 or 64
    _machine = platform.machine().lower()
    # If we got here, import succeeded -- basic arch is compatible
    _RUST_ENGINE_AVAILABLE = True
except ImportError as exc:
    _log.warning(
        "Rust combat engine not available (%s). Falling back to Python engine "
        "(~10-50x slower). Install: cd simulator/core/rust_engine && maturin develop --release",
        exc,
    )
except OSError as exc:
    _log.warning(
        "Rust combat engine failed to load (architecture mismatch: %s). "
        "Falling back to Python engine (~10-50x slower). "
        "Rebuild for current interpreter: cd simulator/core/rust_engine && maturin develop --release",
        exc,
    )
```

### Pattern 4: Context Manager with Safe Cleanup
**What:** `__enter__`/`__exit__` that always re-raises original exceptions and logs cleanup failures.
**When to use:** Any resource-owning class (worker pools, database connections, file handles).
**Example:**
```python
class DataLoader:
    def __enter__(self) -> "DataLoader":
        return self

    def __exit__(self, exc_type, exc_val, exc_tb) -> bool:
        try:
            self.close()
        except Exception as cleanup_err:
            _log.warning(
                "DataLoader cleanup failed during __exit__: %s. "
                "Original exception (if any) takes priority.",
                cleanup_err,
            )
        return False  # Never suppress the original exception

    def __del__(self) -> None:
        if self._pool is not None:
            import warnings
            warnings.warn(
                "DataLoader was garbage-collected without being closed. "
                "Use 'with DataLoader(...) as dl:' or call dl.close() explicitly.",
                ResourceWarning,
                stacklevel=2,
            )
            try:
                self.close()
            except Exception:
                pass
```

### Anti-Patterns to Avoid
- **Returning `True` from `__exit__`**: Suppresses the original exception. The user decided this must NEVER happen.
- **Raising in `__del__`**: Python ignores most exceptions in `__del__`; use `warnings.warn(ResourceWarning)` instead.
- **Lazy dependency checks (check at first use)**: User locked import-time checking. Don't defer.
- **Degraded mode for pyarrow**: User decided no degraded mode. Hard crash only.
- **Using `atexit` for pool cleanup**: Unreliable with multiprocessing; context manager is the correct pattern.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Architecture detection | Manual `/proc/cpuinfo` parsing or env vars | `platform.machine()` + `struct.calcsize('P')` | Cross-platform, handles Windows/Linux/macOS/arm64/x86_64 |
| Resource cleanup protocol | Custom `.cleanup()` + `try/finally` everywhere | `__enter__`/`__exit__` context manager | Python convention, `with` statement handles all paths |
| Unclosed resource warning | Custom reference counting | `ResourceWarning` in `__del__` | Python convention (used by `io.FileIO`, `subprocess.Popen`) |
| Rust rebuild hint | Hardcoded maturin command | Adapt `cloud_runner._rust_extension_rebuild_hint()` | Already exists, includes interpreter-specific paths |

## Common Pitfalls

### Pitfall 1: pyarrow ImportError breaks ALL DataLoader imports
**What goes wrong:** Changing `data_loader.py` line 20-23 from silent fallback to hard ImportError means ANY module importing DataLoader will crash if pyarrow is missing -- including tests, notebooks, etc.
**Why it happens:** pyarrow was previously optional; now it's required.
**How to avoid:** This is the intended behavior per user decision. However, ensure tests that don't need DataLoader don't import it transitively. The test file `test_data_loader.py` already imports DataLoader directly, which is correct.
**Warning signs:** CI failures on environments without pyarrow. Ensure pyarrow is in test requirements.

### Pitfall 2: combat_data.json module-level check blocks all combat_engine imports
**What goes wrong:** Adding a module-level check in `combat_engine.py` means importing `CombatEngine` anywhere fails if combat_data.json is missing.
**Why it happens:** The check runs at import time, not at instantiation time.
**How to avoid:** The user decided "hard crash at module import of simulator.core" -- this is intended. However, note that `combat_engine.py` is imported by `game.py`, `engine_wrapper.py`, `cloud_runner.py`, and `benchmark.py`. All of these will fail if the file is missing. Consider whether the check should be at module level in `combat_engine.py` or in `_load_combat_data()` (which is called at instantiation). Given the user said "at import time", the module-level check is correct, but an alternative is to keep the check lazy (in `_load_combat_data`) but with an actionable error message. RECOMMENDATION: Place check in `_load_combat_data()` with actionable FileNotFoundError, since the existing code already defers loading to instantiation and `_COMBAT_DATA_CACHE` is populated lazily. This still satisfies "actionable error at import time" if the user interprets "import time" as "before any game logic runs" rather than literally "at module import".
**Warning signs:** Tests that import combat_engine but don't need combat data will break.

### Pitfall 3: `__del__` unreliability in Python
**What goes wrong:** `__del__` is not guaranteed to run (interpreter shutdown, reference cycles), and exceptions in `__del__` are printed to stderr but otherwise ignored.
**Why it happens:** CPython garbage collection limitations.
**How to avoid:** Use `warnings.warn(ResourceWarning)` which is the stdlib convention. Wrap `self.close()` in a bare `except Exception: pass` to prevent noise. The `__del__` is a best-effort diagnostic, not a reliable cleanup mechanism -- the context manager is the reliable path.
**Warning signs:** ResourceWarning appearing during interpreter shutdown is normal.

### Pitfall 4: Multiprocessing Pool.close() can hang
**What goes wrong:** `pool.close()` followed by `pool.join()` can hang if worker processes are stuck.
**Why it happens:** Worker processes may be blocked on I/O, deadlocked, or crashed.
**How to avoid:** Consider using `pool.terminate()` as a fallback with a timeout. However, the existing `close()` method already uses `close()` + `join()`, which is the standard pattern. For `__exit__`, wrapping in try/except is sufficient per user decision.
**Warning signs:** Test hangs during cleanup.

### Pitfall 5: Rust `__version__` attribute doesn't exist yet
**What goes wrong:** CONTEXT.md says "Rust extension module exposes a `__version__` attribute for programmatic version comparison" but the current Rust code has no such attribute.
**Why it happens:** This is a new requirement -- `lib.rs` must be modified to expose version info.
**How to avoid:** Add a module-level function or constant in `lib.rs` via PyO3. Read version from `Cargo.toml` or hardcode it. Simplest: add `#[pyfunction] fn __version__() -> &str { env!("CARGO_PKG_VERSION") }` and register in the module.
**Warning signs:** Test for version attribute fails until Rust side is updated.

### Pitfall 6: combat_data.json is checked-in, not generated
**What goes wrong:** CONTEXT.md example says "Regenerate with: python -m simulator.generate_combat_data" but no such module exists. The file is synced from external TFT data and checked into git.
**Why it happens:** The example in CONTEXT.md is illustrative, not literal.
**How to avoid:** The error message should say `git checkout -- simulator/data/combat_data.json` or "ensure you have a complete repository checkout" instead of referencing a non-existent generator.
**Warning signs:** Users trying to run the non-existent generation command.

### RSMG-01/02: DataLoader Context Manager
```python
# Add to DataLoader class in models/data_loader.py

def __enter__(self) -> "DataLoader":
    return self

def __exit__(self, exc_type, exc_val, exc_tb) -> bool:
    try:
        self.close()
    except Exception as cleanup_err:
        _log.warning(
            "DataLoader worker pool cleanup failed during __exit__: %s. "
            "Original exception (if any) takes priority.",
            cleanup_err,
        )
    return False  # Never suppress the original exception

def __del__(self) -> None:
    if getattr(self, '_pool', None) is not None:
        import warnings
        warnings.warn(
            "DataLoader was garbage-collected without being closed. "
            "Use 'with DataLoader(...) as dl:' or call dl.close() explicitly.",
            ResourceWarning,
            stacklevel=2,
        )
        try:
            self.close()
        except Exception:
            pass
```

## Open Questions

1. **combat_data.json check: module-level vs _load_combat_data()?**
   - What we know: User said "hard crash at module import of simulator.core." But there is no `simulator/core/__init__.py` -- it's an implicit namespace package. The check would have to be in `combat_engine.py` itself.
   - What's unclear: If we put a module-level file existence check in `combat_engine.py`, it will fire on ANY import of CombatEngine, even in tests that mock it. Putting it in `_load_combat_data()` still fires before any game logic but only when actually creating an engine.
   - Recommendation: Place the check in `_load_combat_data()` with actionable FileNotFoundError. This satisfies the spirit of the requirement ("actionable error before game logic runs") while being less disruptive to test imports. The user's wording "at import time" in the context of "simulator.core" likely means "at engine initialization time" given the code structure.

2. **Rust `__version__` scope**
   - What we know: User wants `__version__` attribute on the extension module for programmatic version comparison.
   - What's unclear: Whether to modify `lib.rs` in this phase (requires Rust build) or just add the Python-side check that gracefully handles its absence.
   - Recommendation: Add both: a `#[pyfunction] fn engine_version()` in `lib.rs` AND a Python-side `getattr` check that logs a warning if version is missing. This makes the phase self-contained even if the Rust code can't be rebuilt immediately.

3. **Removing `if pq is None` guards after DEPV-01**
   - What we know: Once pyarrow import is mandatory, all `if pq is None: return` guards are dead code.
   - What's unclear: Whether to remove them (cleaner) or leave them (safer, in case someone reverts the import change).
   - Recommendation: Remove them. Dead code is misleading and the import-time check is the single source of truth. This is consistent with the "no degraded mode" decision.
