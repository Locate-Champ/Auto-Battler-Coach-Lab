Rust Combat Engine Rewrite Plan
Context
The TFT simulator's combat engine (86% of runtime) is 11,000+ lines of pure Python running at 0.87s/game. A Rust rewrite via PyO3 targets 15-30x speedup (~0.03-0.06s/game), enabling 1M games in ~20-35 min on 32 cores vs 7.6 hours today. The user plans to build a more in-depth model system on top of this, making sustained high-throughput simulation critical.

Why skip Python-level optimizations: The Rust engine replaces the entire combat hot path. Python-level fixes to code being replaced would be wasted effort.

Both engines kept: Python engine remains as fallback/reference. A flag switches between them for debugging and validation.

FFI Boundary Design
The boundary is clean - Python sends simple data in, Rust returns simple data out. No shared mutable state, no callbacks across the boundary.

What stays in Python:
simulator/game/game.py - 8-player orchestration, economy, rounds
simulator/game/player.py - build_combat_team() constructs unit specs
simulator/game/collector.py - reads combat results for training data
simulator/cloud_runner.py - multiprocessing batch runner
What moves to Rust:
Combat tick loop, all per-tick unit processing
Damage calculation, armor/MR mitigation, crit, shields
Targeting, movement, pathfinding on hex grid
99 champion ability handlers
73+ item combat effects (on_hit, passive, etc.)
33+ trait combat-time effects (Warden shields, Slayer AD, Zaun shimmer, etc.)
DOT system, sunder/shred expiry, CC (stun/fear/taunt/root)

Use usize indices instead of &Unit references to avoid borrow checker fights
Vec<Unit> as arena, Option<usize> for target references

Phase 2: Combat Loop Foundation (3-4 days)
Goal: Basic auto-attack combat works end-to-end.

tick() main loop - advance time by 0.033s, process all units
process_unit_tick() state machine:
IDLE -> find target -> MOVING or ATTACKING
MOVING -> A* pathfinding, move toward target
ATTACKING -> check range, attack cooldown, windup, apply damage
CASTING -> cast progress timer, then execute ability
STUNNED -> decrement stun, then IDLE
find_target() - iterate enemies, compute hex distance, select by TargetingType
calculate_damage() - base damage -> damage amp -> crit -> armor/MR mitigation -> damage reduction
apply_damage() - shields first, then HP, check death, mana on damage taken (1% pre-mit + 3% post-mit)
Mana generation on auto-attack (role-based: ADCarry=10, APCaster=7, Tank=5, etc.)
run_combat() loop: tick until one team dead or max_time
Return result dict via PyO3
Key reference: combat_engine.py:3887-3960 for tick loop, combat_engine.py:2858-2903 for damage calc.

Ability variable access - combat_data.json variables are lists [0, 1star, 2star, 3star]:


fn star_val(var: &serde_json::Value, star: usize, default: f64) -> f64 {
    var.as_array()
        .and_then(|arr| arr.get(star))
        .and_then(|v| v.as_f64())
        .unwrap_or(default)
}

Key Technical Decisions
RNG
rand crate with StdRng::seed_from_u64(seed). Won't match Python's random.random(), but deterministic within Rust. Fine for ML training data.

Memory Layout
Vec<Unit> arena with index-based references. target_idx: Option<usize> instead of pointers. Cache-friendly iteration, avoids borrow checker complexity. When a unit dies, mark is_alive = false rather than removing from Vec (preserves indices).

combat_data.json
serde_json::from_str() once at init, stored as HashMap<String, serde_json::Value>. Same 273KB file the Python engine uses.

Multiprocessing Compatibility
Each Python worker process creates its own RustCombatEngine instance. No shared state between workers. The Rust engine is Send but not shared across threads within a single process (matches current Python pattern).

Multi-Server / Multi-Droplet Deployment
What Already Exists
The cloud runner already supports sharding and aggregation:


# Shard 1 of 4 (on droplet 1):
python -m simulator.cloud_runner --games 1000000 --num-shards 4 --shard-index 0 \
  --output /app/results/shard_0 --workers 4

# Shard 2 of 4 (on droplet 2):
python -m simulator.cloud_runner --games 1000000 --num-shards 4 --shard-index 1 \
  --output /app/results/shard_1 --workers 4

# After all shards finish, merge locally:
python -m simulator.aggregate_results results/shard_0 results/shard_1 results/shard_2 results/shard_3 \
  --output results/merged
Sharding uses deterministic seed partitioning (cloud_runner.py:120-138) so shards never overlap. Checkpoint/resume works per-shard.

Updated Dockerfile (with Rust engine)

FROM python:3.12-slim AS builder

# Install Rust toolchain for building the engine
RUN apt-get update && apt-get install -y curl build-essential && \
    curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
ENV PATH="/root/.cargo/bin:${PATH}"

# Build Rust combat engine
WORKDIR /app
COPY simulator/core/rust_engine/ simulator/core/rust_engine/
RUN pip install maturin && \
    cd simulator/core/rust_engine && \
    maturin build --release && \
    pip install target/wheels/*.whl

# Final image (no Rust toolchain needed at runtime)
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.12/site-packages/ /usr/local/lib/python3.12/site-packages/
COPY requirements-simulator.txt requirements.txt
RUN pip install --no-cache-dir -r requirements.txt
COPY simulator/ simulator/
COPY data/api/processed/ data/api/processed/

ENTRYPOINT ["python", "-m", "simulator.cloud_runner"]
CMD ["--games", "100", "--workers", "4", "--engine", "rust", "--output", "/app/results"]
Multi-stage build: Rust compiles in the builder stage, only the compiled .so/.pyd is copied to the slim runtime image.

Orchestration Script
New file: scripts/run_distributed.sh (or .py) that:

Provisions N droplets via DigitalOcean API (or uses pre-existing ones)
Pushes Docker image to a registry (DOCR or Docker Hub)
Launches shards on each droplet via SSH:

for i in $(seq 0 $((NUM_DROPLETS - 1))); do
  ssh root@${DROPLET_IPS[$i]} \
    "docker run -v /results:/app/results tft-sim \
      --games $TOTAL_GAMES --num-shards $NUM_DROPLETS --shard-index $i \
      --workers $(nproc) --engine rust --output /app/results/shard_$i"
done
Monitors progress by tailing checkpoint.json on each droplet
Collects results via rsync/scp when shards complete
Aggregates locally: python -m simulator.aggregate_results shard_*/

Alternative: DigitalOcean App Platform / Kubernetes
For recurring runs, consider:

DO App Platform: Define a job spec that runs N shard containers, auto-scales
Kubernetes Job: parallelism: N with shard index from JOB_COMPLETION_INDEX
DO Managed K8s: Spin up node pool, run Job, tear down
These are more setup effort but better for scheduled/recurring batch runs. The simple SSH script is fine for ad-hoc runs.

Result Collection Flow

Droplet 1 ──shard_0/── ┐
Droplet 2 ──shard_1/── ├──rsync──> Local ──aggregate──> merged/
Droplet 3 ──shard_2/── │           results/             summary.json
Droplet 4 ──shard_3/── ┘                                chunk_*.parquet
Each shard produces its own chunk_*.parquet files + summary.json. The aggregation step merges summaries and the training data can be loaded directly from shard directories (the data loader already supports multi-directory input).
